# SoftZoom — Product Specification

**Version:** 0.1 (Concept / MVP)\
**Status:** Draft

## 1. Overview

**SoftZoom** — визуальный AI-интерфейс для исследования, понимания и изменения сложных кодовых баз, в том числе созданных с помощью vibe coding.

Система использует AI-агента для построения многоуровневых интерактивных схем, отражающих фактическую реализацию приложения.

Пользователь последовательно исследует кодовую базу, выбирает интересующие компоненты и формулирует изменения непосредственно в их визуальном контексте.

**Основная идея:** заменить значительную часть ручного исследования кода и текстового описания контекста визуальной навигацией и выбором компонентов.

## 2. Problem Statement

Изменение сложных приложений, особенно созданных с помощью AI, сопряжено с несколькими проблемами:

- **Сложность навигации.** Необходимо находить нужные сущности и понимать взаимосвязи между ними.
- **Высокая стоимость формирования контекста.** Пользователь вынужден объяснять агенту, о какой части приложения идёт речь.
- **Ненадёжность интерпретации AI.** Агент может формировать ошибочные представления об архитектуре, подменяя существующую реализацию предполагаемой.
- **Когнитивная перегрузка.** Большое количество файлов, компонентов и зависимостей затрудняет понимание системы.
- **Сложность контроля изменений.** Трудно определить область воздействия правки и проверить её последствия.

## 3. Goals

1. Ускорить исследование незнакомой кодовой базы.
2. Снизить когнитивную нагрузку благодаря визуальному представлению.
3. Минимизировать необходимость текстового описания контекста.
4. Обеспечить фактическую обоснованность архитектурных схем.
5. Упростить передачу контекста AI-агенту для изменения кода.
6. Повысить предсказуемость изменений и упростить их проверку.

## 4. Core Principles

### 4.1. Agent-generated, Code-grounded

Схемы самостоятельно строятся AI-агентом на основе исходного кода.

Агент отвечает за:

- Выделение сущностей и подсистем.
- Семантическую группировку компонентов.
- Определение и визуализацию связей.
- Выбор подходящего уровня абстракции.
- Построение понятного человеку представления.

Каждый существенный элемент схемы должен быть обоснован фактической реализацией.

Семантическая интерпретация допустима и необходима, однако она не должна противоречить наблюдаемым фактам.

### 4.2. As-is over Ideal

**Текущее состояние кодовой базы всегда приоритетнее предполагаемой правильной архитектуры.**

Агент должен отображать систему такой, какая она есть, даже если:

- Ответственности компонентов смешаны.
- Архитектурные границы нарушены.
- Существуют циклические зависимости.
- Реализация противоречит распространённым паттернам.
- Названия компонентов не соответствуют их фактическому поведению.

Агент не должен мысленно рефакторить или идеализировать архитектуру.

### 4.3. Progressive Disclosure

Детализация системы увеличивается по мере погружения пользователя.

Каждый переход раскрывает выбранную область на более подробном уровне.

Пользователь не должен одновременно интерпретировать всё приложение.

### 4.4. Lazy, Scoped Generation

**SoftZoom не строит подробную схему всей кодовой базы заранее.**

При переходе в конкретную подсистему:

- Анализируется выбранная область.
- Генерируется схема только этой области.
- Остальные подсистемы не детализируются.
- Значимые внешние зависимости могут отображаться как граничные узлы.
- Дальнейший анализ происходит только при необходимости.

Преимущества:

- Более быстрое построение схем.
- Меньше вычислительных затрат.
- Меньше визуального шума.
- Более точная интерпретация благодаря ограниченному контексту.

Допускается предварительная лёгкая индексация репозитория для поиска файлов и определения потенциальных связей. Она не должна требовать полной семантической визуализации.

### 4.5. Explore → Modify

Исследование и изменение кода — части единого пользовательского процесса.

Любой выбранный компонент или набор компонентов можно непосредственно использовать как контекст для AI-правки.

Пользователю не нужно заново описывать расположение компонентов или перечислять соответствующие файлы.

### 4.6. Current Code as Source of Truth

Кодовая база является единственным источником истины о текущей реализации.

Схемы являются временными представлениями конкретного состояния репозитория, а не самостоятельной архитектурной документацией.

После изменения кода связанные схемы должны актуализироваться.

## 5. Visualization Model

### 5.1. Semantic Zoom

SoftZoom использует графовую модель с несколькими уровнями абстракции.

| Level | Scope        | Description                                                                     |
| ----- | ------------ | ------------------------------------------------------------------------------- |
| L4    | Applications | Приложения, проекты и их взаимодействия                                         |
| L3    | Subsystems   | Архитектурные группы, модули и подсистемы                                       |
| L2    | Entities     | Классы, сервисы, функции, состояния и другие сущности                           |
| L1    | Behavior     | Конкретное поведение, переходы состояний, условия и последовательности операций |

Уровни определяют масштаб представления, но не навязывают кодовой базе жёсткую иерархию.

Одна сущность может участвовать в нескольких подсистемах.

### 5.2. Graph Representation

Модель представляет собой граф с узлами и связями.

**Nodes:**

- Приложения.
- Подсистемы.
- Компоненты.
- Сущности.
- Состояния.
- Поведенческие элементы.

**Edges:**

- Зависимости.
- Вызовы.
- Передача данных.
- События.
- Переходы состояния.
- Другие отношения, подтверждённые кодом.

Агент самостоятельно определяет релевантные типы узлов и связей для конкретного масштаба.

### 5.3. Dynamic Diagram Generation

Форма визуализации зависит от предметной области.

Например:

- Архитектура → Component graph.
- Последовательность вызовов → Sequence diagram.
- Работа с состоянием → State machine.
- Передача данных → Data-flow diagram.

Это не обязательный закрытый набор. Агент должен выбирать представление, лучше всего объясняющее текущую реализацию.

### 5.4. Evidence and Traceability

Для значимых элементов схемы должна существовать возможность перейти к соответствующему коду.

Не требуется разделять визуализацию на «факты» и «семантику» или заставлять пользователя выбирать между ними.

Вместо этого всё представление должно быть основано на проверяемых фактах.

Если конкретная связь не может быть установлена достоверно, агент не должен изображать её как подтверждённую. При необходимости неполнота анализа обозначается в интерфейсе.

## 6. User Experience

### 6.1. Initial Exploration

1. Пользователь открывает репозиторий.
2. SoftZoom определяет общую структуру проекта.
3. Агент генерирует начальную высокоуровневую схему.
4. Пользователь выбирает интересующую область.

### 6.2. Scoped Navigation

1. Пользователь выбирает подсистему.
2. SoftZoom определяет её фактические границы и релевантный код.
3. Агент строит более детальную схему выбранной области.
4. Другие области остаются свёрнутыми.
5. При необходимости отображаются внешние связи.
6. Пользователь может продолжать погружение или возвращаться на предыдущие уровни.

**Ключевое требование:** переход в подсистему не должен запускать полную генерацию схем соседних подсистем.

### 6.3. Visual Context Selection

Пользователь может:

- Выделить один или несколько узлов.
- Выделить связи или конкретное поведение.
- Расширить выделение за счёт зависимостей.
- Удалить ненужные компоненты из контекста.
- Посмотреть соответствующие исходники.

Выделение формирует структурированный контекст для дальнейшего запроса.

### 6.4. AI-Assisted Modification

1. Пользователь выделяет область на схеме.
2. Вводит короткую инструкцию на естественном языке.
3. SoftZoom формирует контекст на основе выбранных элементов и связанных исходников.
4. AI-агент анализирует необходимые зависимости и выполняет изменение.
5. Пользователь получает результат и может проверить его.

Если для безопасной правки требуется выйти за пределы выбранной области, система должна явно показать необходимость расширения контекста или области изменений.

### 6.5. Change Verification

После выполнения правки SoftZoom предоставляет:

- Code diff.
- Список затронутых компонентов.
- Результаты доступных проверок и тестов.
- Обновлённое визуальное представление изменённой области.

При наличии достаточных данных система может визуально показывать изменения в связях и поведении.

## 8. Technical Approach

Предварительная архитектура состоит из пяти компонентов.

### 8.1. Repository Analyzer

- Получает доступ к актуальной версии исходного кода.
- Индексирует структуру репозитория.
- Предоставляет агенту средства поиска, чтения файлов и анализа связей.
- Поддерживает привязку выводов к исходникам.

### 8.2. Scoped Diagram Agent

- Получает выбранную область и желаемый уровень детализации.
- Анализирует релевантный код.
- Строит семантический граф.
- Генерирует представление графа.
- Учитывает только необходимые внешние зависимости.

Агент может использовать статический анализ и другие доступные инструменты проверки фактов.

### 8.3. Visual Explorer

- Отображает диаграммы.
- Поддерживает навигацию между уровнями.
- Позволяет выделять узлы и связи.
- Управляет раскрытием и сворачиванием подсистем.
- Показывает ссылки на исходный код.

### 8.4. Context Builder

Преобразует визуальное выделение в структурированный контекст:

- Выбранные сущности.
- Соответствующие файлы.
- Релевантные зависимости.
- Исходная задача пользователя.
- Ограничения области изменений.

Контекст должен быть достаточно полным для задачи, но не содержать заведомо лишних данных.

### 8.5. Change Agent

- Получает структурированный контекст и намерение пользователя.
- Исследует дополнительные зависимости при необходимости.
- Формирует и выполняет изменения.
- Запускает доступные проверки.
- Предоставляет diff.
- Инициирует обновление затронутых схем.

## 9. Consistency and Performance

### 9.1. Incremental Analysis

Необходимо избегать повторного анализа неизменённого кода.

Результаты могут кэшироваться с привязкой к версии репозитория и области анализа.

При изменении файлов соответствующие части кэша инвалидируются.

### 9.2. Scoped Resource Consumption

Объём анализа должен зависеть преимущественно от размера выбранной области, а не всего репозитория.

Это важная целевая характеристика, а не гарантия постоянной сложности: общие зависимости и динамические связи могут требовать более широкого анализа.

### 9.3. Model Consistency

Разные схемы одного состояния кода не должны противоречить установленным фактам.

Одинаковый код не обязан приводить к пиксельно идентичным схемам.

Главное требование — фактическая обоснованность и согласованность представлений.

### 9.4. Snapshot Consistency

Каждая схема должна соответствовать определённому состоянию репозитория: ветке, коммиту и учтённым локальным изменениям.

Устаревшие схемы не должны представляться как актуальные.

## 10. MVP Scope

Первый MVP должен проверять основной продуктовый цикл:

**Explore → Zoom → Select → Prompt → Change → Verify**

В MVP входят:

- Поддержка одного выбранного языка или технологического стека.
- Подключение локального репозитория.
- Базовый анализ структуры проекта.
- Генерация схем на L4–L2.
- Ограниченная визуализация L1 для поддерживаемых типов поведения.
- Переход между уровнями.
- Генерация только выбранной области.
- Выделение компонентов.
- Передача визуального контекста AI-агенту.
- Выполнение правки и просмотр diff.
- Обновление изменённой области схемы.

Полная поддержка произвольных репозиториев, универсального runtime-анализа и всех видов поведения не входит в MVP.

## 11. Success Metrics

SoftZoom необходимо сравнивать с обычным workflow разработки при помощи AI coding agent.

| Metric                  | What to measure                                              |
| ----------------------- | ------------------------------------------------------------ |
| Time to Context         | Время от постановки задачи до нахождения нужного контекста   |
| Prompt Effort           | Количество текста и взаимодействий для формулирования задачи |
| Context Accuracy        | Полнота и релевантность выбранного контекста                 |
| Change Success Rate     | Доля изменений, успешно прошедших заданные проверки          |
| Unintended Changes      | Количество непредусмотренных изменений                       |
| Diagram Generation Cost | Время и вычислительная стоимость построения схем             |

Основная гипотеза:

**Визуальное исследование и формирование контекста позволяют быстрее и надёжнее изменять сложные приложения, чем взаимодействие только через текстовый AI-агент.**

## 12. Main Risks

**R1. Hallucinated Architecture**

Агент может создавать логически убедительные, но неверные схемы.

Mitigation: приоритет текущей реализации, проверяемые ссылки на код, исключение неподтверждённых утверждений.

**R2. Incomplete Dependency Context**

Локальный анализ может пропускать важные внешние зависимости.

Mitigation: анализ границ, возможность расширения контекста и явное обозначение неизвестных связей.

**R3. Diagram Complexity**

Даже локальный граф может оказаться слишком сложным.

Mitigation: семантический zoom, ограничение детализации, управление видимостью компонентов.

**R4. Expensive Agent Analysis**

Генерация сложных схем может быть медленной.

Mitigation: lazy generation, ограниченный scope, инкрементальный анализ и кэширование.

**R5. False Sense of Safety**

Фактически обоснованная схема может быть неполной, особенно при динамическом поведении.

Mitigation: не приравнивать отсутствие отображённой связи к доказательству её отсутствия; использовать проверки кода и тесты после изменений.

## 13. Non-Goals

SoftZoom не предназначен для:

- Автоматического исправления архитектуры приложения.
- Принудительного приведения кода к архитектурным best practices.
- Построения исчерпывающей схемы всего репозитория перед началом работы.
- Замены исходного кода визуальной моделью.
- Гарантированного доказательства корректности изменений.
- Обязательного ручного создания или редактирования архитектурных диаграмм.

## 14. Product Definition

**SoftZoom is an AI-powered, code-grounded visual interface for exploring and modifying complex software systems.**

It progressively generates scoped semantic views of the current codebase, allowing developers to navigate architecture, select relevant components, express changes with minimal prompting, and verify the results.

**Core philosophy:**

- AI generates the model.
- Current code grounds the model.
- Users control the scope and intent.
- Analysis follows the user's focus.
- Exploration and modification form one continuous workflow.

**Ключевое отличие SoftZoom:** это не статический визуализатор кода и не ещё один чат с coding agent. Это визуальный интерфейс, который позволяет человеку управлять контекстом AI-изменений через непосредственное взаимодействие с фактически обоснованной моделью приложения.

Спека фиксирует продуктовую концепцию и границы MVP, не привязываясь пока к конкретному AI-агенту, формату графа или UI-фреймворку.
